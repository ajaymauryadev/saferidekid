# Prompt 03 authentication evidence

The final HTML's login card, two-column art, blue-white surfaces, van illustration and mobile form hierarchy were inspected before implementation. [React desktop](react-login-1440.png) versus [HTML desktop](reference-login-1440.png), and [React mobile](react-login-390.png) versus [HTML mobile](reference-login-390.png) show the visual comparison. React removes the simulation's demo IDs, `demo123`, floating preview and local-only warning; it uses one real login form. [Signed-in customer 390px](react-customer-after-signup-390.png) shows the customer role reached after signup.

`npm run verify:auth` starts isolated MongoDB, API, Vite and Chrome instances. It verified customer signup and automatic role-based routing, the same customer session opening school and booking shells, wrong-role redirect, logout and denial of the revoked cookie, owner login, driver invitation and one-time activation, and driver login. Login screenshots at 390 and 1440px had no horizontal overflow or page errors.

API tests cover: duplicate and invalid credentials, policy acceptance timestamps and version, one-time owner bootstrap, HttpOnly/SameSite cookie, origin and CSRF denial, logout and session-switch revocation, invitation reuse denial, owner-assisted reset reuse denial, deactivation, 401/403/cross-business IDOR, repeated login lockout, explicit audited owner driver-duty ability, and session expiry. The auth API never stores raw session or invitation tokens in MongoDB; it stores SHA-256 token hashes. Passwords use bcrypt cost 12.

No SMS or email recovery is configured. The owner can issue a one-time reset token and share it through a trusted channel. Student accounts remain optional and cannot be publicly created; a future approved student profile and guardian process must exist before provisioning one. School, booking, payment and trip endpoints remain outside this phase; their signed-in routes display coming-soon states, not invented protected data.
